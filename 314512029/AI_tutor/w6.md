### Question 1

**Statement:** If a search reduces the remaining candidate range by approximately half after every constant-time step, its worst-case number of steps grows logarithmically with the original range size.

**My answer:** True. After `k` halvings, a range of size `n` has about `n / 2^k` candidates. Reaching one candidate requires `2^k` to be about `n`, so `k` is about `log2(n)`.

**AI feedback:** Correct. The logarithmic result comes from repeatedly dividing the problem size by a constant factor.

### Question 2

**Statement:** A recursive bisection search that passes `L[:mid]` or `L[mid:]` must take O(log n) time because it makes only O(log n) recursive calls.

**My initial answer:** True. The list is halved on each recursive call, so I thought the recursion depth alone determined the running time.

**AI hint:** In Python, does creating `L[:mid]` merely pass two indices, or does it construct a new list? Add the numbers of elements copied along one recursive path: approximately `n/2 + n/4 + n/8 + ...`.

**My revised answer:** False. The search performs O(log n) comparisons, but every slice copies elements. The copied lengths form a geometric sum smaller than `n`, so the total slicing work is O(n). Passing the original list with low and high indices avoids that cost and gives O(log n) time.

**AI feedback:** Correct. Counting calls is insufficient when setting up each call has a size-dependent cost.

### Question 3

**Statement:** Iterative factorial and the standard recursive factorial can both have linear order of growth even if the recursive version takes longer in an actual timing experiment.

**My answer:** True. Both perform one multiplication for each value down to the base case, giving O(n) work. Function-call overhead changes constants but not the order of growth.

**AI feedback:** Correct. Algorithms can share an asymptotic class while having different practical running times.

### Question 4

**Statement:** Any recursive function that makes two recursive calls is necessarily exponential.

**My answer:** False. The sizes of the recursive subproblems matter. Two calls on size `n/2` produce a different recurrence from two calls on sizes near `n`, and memoization or overlapping work can also change the cost.

**AI feedback:** Correct. Naive recursive Fibonacci and Towers of Hanoi have exponential recursion trees, but the number of calls alone does not prove exponential growth.

### Question 5

**Statement:** An algorithm that explicitly generates every subset of an `n`-element set cannot run in polynomial time in `n`, because its output already contains `2^n` subsets.

**My answer:** True. Each element can either be excluded or included, producing `2^n` distinct subsets. Writing every subset therefore requires at least exponential output work.

**AI feedback:** Correct. Output size can impose a lower bound on the time required to generate the complete result.

## My Misconception

**Now:** I understand that I must include the work performed at each recursion level. Bisection with indices does O(1) setup per level, but bisection with Python slices copies a decreasing sequence of list portions whose total length is O(n).

### Explanation and Reflection

**Why my solution works:** Throughout the loop, `low` and `high` bound the first possible qualifying position. If `times[mid] < target`, neither `mid` nor any earlier position can qualify, so setting `low = mid + 1` is safe. Otherwise, `mid` may be the first qualifying position, so setting `high = mid` keeps it while removing later candidates. When `low == high`, that position is the first possible answer. If it equals `len(times)`, no qualifying event exists.

**Time and space complexity:** Each iteration reduces the candidate interval by about half and performs constant work. The worst-case time is O(log n). The algorithm stores only three indices, so its extra space is O(1). It does not create list slices.

**What idea from the OCW lecture did I transfer to this new problem?** I transferred index-based bisection from exact search to boundary search in a sorted event log.

**How this connects to Lab 06 and the project discussion:** MOOS applications publish timestamped data, and mission logs can contain many ordered events. Efficient boundary lookup can locate the first event at or after a requested time without scanning the entire log. The same idea could support later project tools that inspect or replay recorded mission data.

**One thing I understand better now:** I understand why finding one matching duplicate is different from finding the first matching duplicate, and why the equality case must keep searching toward the left.

**One thing I am still unsure about:** How binary search should be adapted when log entries are not already sorted or when new events arrive continuously.

**AI follow-up:** Binary search requires sorted data. An unsorted fixed log must first be sorted or scanned linearly. For a live stream, maintaining an ordered structure or appending timestamps that are already chronological allows later binary searches, but updates and queries introduce additional design tradeoffs.
