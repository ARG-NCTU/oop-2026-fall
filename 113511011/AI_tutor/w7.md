### ① Check My Understanding

**Question 1 — Constant Complexity**  
**True or False:** Every Python function containing a `for` loop must take at least `O(n)` time, where `n` is the input size.

**Model answer:** False.

**Reason:** A loop over `range(10)` performs a fixed number of iterations regardless of `n`. Assuming constant work per iteration, its time complexity is `O(1)`. We must identify whether the iteration count *depends on input size*.

**Question 2 — Binary Search and Slicing**  
**True or False:** Since binary search halves the search space each time, the following Python implementation necessarily runs in `O(log n)` time:

```python
def contains_by_slicing(L, target):
    if len(L) == 0:
        return False
    if len(L) == 1:
        return L[0] == target
    mid = len(L) // 2
    if L[mid] > target:
        return contains_by_slicing(L[:mid], target)
    return contains_by_slicing(L[mid:], target)
```

**Model first answer:** True.

**AI hint (model):** `L[:mid]` creates a new list. If the input has `n` elements, how many elements must be copied at the first, second, and third recursive levels? Are the recursive calls themselves the only work?

**Model revised answer:** False.

**Reason:** The recursion depth is `O(log n)`, but slicing copies roughly `n/2 + n/4 + n/8 + ...` list-element references across the calls. This geometric sum is `O(n)`. Hence the implementation has a **tight worst-case bound of O(n)**. The index-based version avoids copying the list and has `O(log n)` time.

**Question 3 — Adding Versus Multiplying Costs**  
**True or False:** Once we have summed *all* slicing costs as `O(n)` and *all* recursion-control costs as `O(log n)`, we must multiply them and obtain `O(n log n)`.

**Model answer:** False.

**Reason:** These are already two **total** costs for different types of work, so they are added: `O(n) + O(log n) = O(n)`. Multiplication is useful when the same per-operation cost is incurred repeatedly, such as `n` iterations each performing `O(n)` work. A coarse bound `O(n) × O(log n)` is valid if `O(n)` is a per-level upper bound, but it is not tight for the shrinking slices.

**Question 4 — Factorial**  
**True or False:** The iterative factorial algorithm and the straightforward recursive factorial algorithm are both `O(n)` time under the lecture's constant-cost arithmetic assumption.

**Model answer:** True.

**Reason:** Iteration performs `n` constant-work rounds. Recursion follows a single chain `n, n-1, ..., 1` with constant work per call. However, the recursive version uses `O(n)` call-stack space, while the iterative version uses `O(1)` auxiliary space in the simplified model.

**Question 5 — Hanoi versus Counting Hanoi Moves**  
**True or False:** The recursive algorithm that **outputs every move** in Towers of Hanoi takes exponential time, but a separate recursive function that only **returns the number of moves** using `2 * count(n-1) + 1` makes only one recursive call per level.

**Model answer:** True.

**Reason:** Outputting all required moves entails `2^n - 1` move records in the standard algorithm and takes `Theta(2^n)` time if each record is constant cost. `count(n)` computes the same number without generating the moves; its recurrence for running time is `C(n)=C(n-1)+O(1)`, or `O(n)` under constant-cost arithmetic. The *value* returned by `count(n)` is exponential, but its *running time* need not be.

### ② My Misconception

**Before:**  
I focused too much on recursion depth. Since binary search halves the list, I assumed any recursive implementation using bisection would be `O(log n)`, overlooking the cost of list slicing.

**Now:**  
I now distinguish recursion depth from total work. In a slicing implementation, the cost of creating each new list decreases over time, so the total must be summed as `n/2 + n/4 + ... = O(n)`. I also confirmed why slicing cost `O(n)` and recursion-control cost `O(log n)`, when already summed over all calls, must be added rather than multiplied. Big O measures the work actually done, not the magnitude of the returned answer.

### 1. Today's Challenge

**Core concept from today's OCW lecture:**  
The lecture compares recursive bisection search with list slicing (`O(n)` total copying) and index-based bisection search (`O(log n)`). This challenge transfers the **index-based approach** to a new task that must handle duplicate target values.

**Problem statement:**  
Given a sorted list `numbers` in nondecreasing order and an integer `target`, return the **first and last indices** at which the target occurs. If it is not present, return `(-1, -1)`.

**Input / Output specification:**

```python
find_target_range(numbers, target) -> tuple[int, int]
```

**Constraints:**

1. `numbers` is sorted in nondecreasing order and may contain duplicates.
2. `numbers` may be empty; integers may be negative.
3. Do not use list slicing, `list.index`, or `list.count`.
4. Aim for `O(log n)` worst-case time and `O(1)` auxiliary space.
5. Use only lists, indices, `while`, conditionals, and functions (no external libraries).

**Example 1**

**Most useful hint/question (model):**  
“Ordinary binary search can stop at *any* matching element. What happens if the target appears four times? Can you search for the first position whose value is `>= target`, and separately for the first position whose value is `> target`?”

**What I learned:**  
A sorted list allows us to find **boundaries** rather than merely confirm membership. The first index satisfying `numbers[i] >= target` is a *lower bound*; the first index satisfying `numbers[i] > target` is an *upper bound*. If the target exists, the answer is `(lower_bound, upper_bound - 1)`.

### 4. My Revision

**Did I change my approach?**

- [ ] No
- [x] Yes

**What changed and why:**  
I replaced sequential scanning and slicing with two while-loop binary searches on the half-open interval `[low, high)`. In each iteration, I compare one middle element and discard approximately half of the remaining indices. No new list is built.

```python
low, high = 0, len(numbers)
while low < high:
    mid = (low + high) // 2
    if numbers[mid] < target:
        low = mid + 1
    else:
        high = mid
```

This loop returns the first position with value `>= target`. A similar loop using `numbers[mid] <= target` finds the first position with value `> target`.

**Why the solution works:**  
The lower-bound search maintains the first possible position whose value could be at least `target`. At each step, if `numbers[mid] < target`, all positions through `mid` are too small, so `low = mid + 1`. Otherwise `mid` could still be the first qualifying position, so `high = mid`. The upper-bound search applies the same idea with strict greater-than. Because `numbers` is sorted, all occurrences of `target` form a contiguous block between the two boundaries. An explicit existence check handles missing targets safely.

**Time complexity:**  
Let `n = len(numbers)`. Each binary-search iteration decreases the length of the candidate interval by approximately a factor of two. The two searches together take `O(log n) + O(log n) = O(log n)` time for `n >= 2`; empty and single-element inputs are constant time. No list slices or copies are performed.

**Extra space complexity:**  
Both searches are iterative and store only a constant number of index variables: `low`, `high`, and `mid`. Hence auxiliary space complexity is **O(1)**.

**Why not use slices?**  
A recursive version that repeatedly creates half-list slices may spend `n/2 + n/4 + ... = O(n)` work solely on copying. Keeping the same `numbers` list and moving index boundaries avoids that cost.

### Lecture-specific reminder

A recurrence describing the **answer** is not necessarily a recurrence describing the **running time**. For Towers of Hanoi, the *move count* is `2^n - 1`, but a function that merely computes that number via `2 * count(n-1) + 1` has only one recursive call per level. The function that actually **generates all moves** must do exponential output work. This distinction, together with the hidden cost of Python slicing, is central to the lecture's complexity analysis.
