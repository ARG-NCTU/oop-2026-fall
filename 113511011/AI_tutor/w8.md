### ① Check My Understanding

**Question 1 — Sorting before searching** (pp. 9–10)  
**True or False:** For one membership query on an arbitrary unsorted list, merge sorting first and then binary searching improves the worst-case asymptotic time over linear search.

**My answer:** False. One scan is O(n); preprocessing costs O(n log n) before the O(log n) query.  
**AI follow-up:** What changes if the list stays unchanged and we make K queries?  
**My explanation:** We compare O(Kn) with O(n log n + K log n). Sorting can pay off over many queries. Big O alone does not specify an exact practical break-even point.

**Question 2 — Bubble sort's early exit** (pp. 14–15)  
**True or False:** The lecture's bubble sort stops after a swap-free pass, so already sorted input takes linear time, while worst-case time remains quadratic.

**My answer:** True. A sorted list needs one pass of n−1 comparisons. Reverse order needs repeated passes.  
**AI follow-up:** Does the best case determine Big O for every input?  
**My explanation:** No. Best and worst cases quantify different sets of executions. The early-exit implementation has Θ(n) best-case and Θ(n²) worst-case time for n ≥ 2.

**Question 3 — Selection sort invariant** (pp. 16–18)  
**True or False:** After a completed selection-sort step, its sorted prefix contains the smallest elements selected so far; merely having an internally sorted prefix is insufficient to prove the whole algorithm correct.

**My answer:** True. For example, prefix `[9]` is sorted even if suffix `[1, 2]` contains smaller values.  
**AI follow-up:** State the stronger invariant.  
**My explanation:** After i steps, the first i elements are sorted and none exceeds an element of the remaining suffix. Moving a suffix minimum into the next position preserves both properties. Scanning suffix lengths n, n−1, … gives Θ(n²) work even for sorted input in the lecture implementation.

**Question 4 — Merge sort's total work** (pp. 26–30)  
**True or False:** Merge sort takes O(log n) time because its recursion depth is logarithmic.

**My first answer:** True; the input is halved every time.  
**AI Tutor hint:** At the top merge, how many elements are copied? At the next level, add the work of *both* merges.  
**My revised answer:** False. Every level processes a total of Θ(n) elements, across all subproblems. There are Θ(log n) levels, so total time is Θ(n log n).  
**Explanation:** T(n) = 2T(n/2) + Θ(n). Slicing adds linear work per level and does not change this bound. Depth counts levels, not all work.

**Question 5 — Stability requires a tie rule** (merge code, p. 26)  
**True or False:** If merging tagged records takes the right-hand record whenever keys tie, the resulting merge sort can reorder equal-key records.

**My answer:** True. Two records `(5, 'early')` and `(5, 'late')` placed in different halves can emerge in the opposite order.  
**AI follow-up:** How would you preserve their original relative order?  
**My explanation:** Choose the left record on equal keys. The lecture uses `<` and otherwise takes the right; numeric order is correct, but stable record ordering requires an intentional change. Stability is an extension I inferred from the merge code, not a claim made by the slides.

### ② My Misconception

**Before:** I counted recursive depth and treated it as total running time.  
**Now:** Merge sort branches into two recursive calls. Each level performs Θ(n) aggregate merging work, so logarithmic depth yields Θ(n log n) total work. This differs from a binary search following only one branch.

### ③ Challenge the AI

**Statement challenged:** “O(n log n) is the fastest a sort can be.” (summary, p. 31)

- [x] Oversimplified
- [x] Technically questionable without assumptions
- [ ] Too easy

**Why:** The standard lower bound concerns worst-case comparison sorting of arbitrary keys. It does not prohibit linear best cases or non-comparison algorithms under extra key assumptions. This qualification is my analysis of the slide's broad wording.

**Better question:** “Must a comparison-based sort handle some arbitrary distinct-key input using Ω(n log n) comparisons?” True; the decision tree must distinguish n! possible orders.

### 1. Today's Challenge

**Problem:** Given integer scores in registration order, return `(original_index, score, dense_rank)` records sorted by decreasing score. Equal scores must keep their original registration order. Dense ranks start at 1 and increase by one only when the score changes. Do not mutate the input.

**Input / Output:** `rank_scores(scores: list[int]) -> list[tuple[int, int, int]]`.

**Constraints:** 0 ≤ n ≤ 100000; −1000000 ≤ score ≤ 1000000. Use a merge-sort implementation, lists, tuples, loops and recursion. No `sorted()` or `list.sort()` in the solution. Those built-ins may be used as an independent test oracle. Aim for O(n log n) worst-case time and O(n) auxiliary space.

| Scores | Expected output |
|---|---|
| `[40, 60, 60, 20]` | `[(1, 60, 1), (2, 60, 1), (0, 40, 2), (3, 20, 3)]` |
| `[7, 7, 7]` | `[(0, 7, 1), (1, 7, 1), (2, 7, 1)]` |
| `[]` | `[]` |

**Transfer beyond the lecture:** Sorting plain numbers is insufficient. I must preserve record identity, define ties explicitly and compute ranks in a second pass.

### 2. My Initial Approach — Before AI Help

**My approach:** Repeatedly find the largest remaining score, remove it, and assign the next rank. This resembles selection sort and can take O(n²). I then propose merge sort to improve runtime.

**Concept transferred:** Split into smaller subproblems and merge sorted halves with two pointers. I will attach each original index before splitting.

### 3. AI Tutor Help

- [x] Yes — conceptual hints in this simulated interaction

**AI:** “For scores `[5, 5]`, suppose the two records reach different halves. Your merge chooses the right record on equality. Which registration appears first? Also, should the ranks be 1, 2 or 1, 1?”  
**My response:** Choosing right reverses their original order. Incrementing rank for every record incorrectly separates ties. I need left-first ties and rank changes only between different scores.

### 4. My Revision

I will create `(index, score)` records in input order. A recursive sort returns a new list. During merging I choose the left record when its score is greater **or equal**. After sorting, I scan once and increase a dense-rank counter only when the score differs from the previous score. No input element is changed.

**Trace:** For `[40, 60, 60, 20]`, the merge combines `[(1, 60), (0, 40)]` and `[(2, 60), (3, 20)]`. Taking index 1 before index 2 preserves the tied order. The rank scan assigns `1, 1, 2, 3`.

### Python Program

```python
"""Lecture 12 transfer: stable score ordering and dense ranks."""


def merge_records(left, right):
    """Merge descending-score records, choosing left on ties."""
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i][1] >= right[j][1]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result


def sort_records(records):
    """Return a fresh, stable list sorted by descending score."""
    if len(records) < 2:
        return records[:]
    mid = len(records) // 2
    return merge_records(sort_records(records[:mid]),
                         sort_records(records[mid:]))


def rank_scores(scores):
    """Return (original index, score, dense rank), preserving input."""
    records = sort_records(list(enumerate(scores)))
    result = []
    rank = 0
    previous = None
    for index, score in records:
        if rank == 0 or score != previous:
            rank += 1
        result.append((index, score, rank))
        previous = score
    return result
```

**Why the solution works:** By induction, each recursive result is sorted and stable. At a merge, the next largest remaining record is at one of the two heads. Selecting that head maintains descending order and consumes exactly one record. Left-first equality preserves the original order across halves, while the induction hypothesis preserves it within halves. Appending an exhausted side's remainder preserves both properties. Thus all records appear exactly once in the required order. Equal scores are contiguous, so increasing the rank precisely at score changes gives dense ranks with no gaps.

**Time complexity:** With n records and constant-cost bounded-integer comparisons, T(n) = 2T(n/2) + Θ(n), including slicing and merging. Therefore Θ(n log n) for n ≥ 2; attaching indices and ranking each add Θ(n). Empty and singleton inputs take O(1).

**Space complexity:** Peak auxiliary space is O(n), including record lists, slices and merge outputs; simultaneously live subproblem sizes along a recursive path form a geometric sum. The call stack is O(log n). The returned list uses O(n) space. Cumulative allocations over the whole run may be O(n log n), which is different from peak space. No slices are described as free.
