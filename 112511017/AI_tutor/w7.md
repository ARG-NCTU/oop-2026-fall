1. Statement: Halving a sorted search interval each iteration gives logarithmic worst-case search time when each iteration does constant work.

   Supplied answer: True. After k halvings, the candidate count is about n / 2^k. Reaching a constant-sized interval takes O(log n) iterations.

2. Statement: Copying half of a Python list at every bisection step always preserves O(log n) total time.

   Supplied answer: False. Slices copy elements. The copied lengths can total n/2 + n/4 + ... = O(n), even though the recursion depth is logarithmic. Index bounds avoid these copies.

3. Statement: The lecture's subset generator can return all subsets of an n-element input in polynomial total time.

   Supplied answer: False. It returns 2^n subsets. Materializing lists also copies their contents. For distinct elements, the total number of element occurrences across those lists is n * 2^(n-1) for n >= 1.

4. Statement: The lecture's recursive index-based bisection search uses O(1) auxiliary space because it does not slice the input.

   Supplied answer: False. Its recursive call stack can have O(log n) frames. An iterative implementation can keep only its current bounds and use O(1) auxiliary space.

5. Statement: The lecture's bisection algorithm remains correct if the input is unsorted.

   Supplied answer: False. Discarding half the candidates depends on sorted order. For example, searching for 9 in [9, 1, 5] can discard its position after inspecting the middle value.

### 6. One-Minute Reflection

AI-supplied correctness explanation: During each boundary search, every position before `low` has a value below the target and every position at or after `high` has a value at least the target. The unknown interval is `[low, high)`. Each comparison preserves those facts and strictly shrinks that interval. At termination, `low == high` is the first qualifying index, or the list length if none qualifies. Subtracting the two boundary indices counts exactly the events in the requested window. Empty and reversed windows return zero immediately.

Time complexity: Each search halves its unknown interval and uses one indexed comparison per iteration. Two searches take O(log n) time for n >= 2, with constant work for smaller inputs. Integers have bounded size under the stated constraints. Auxiliary space is O(1), and no list is copied. Sorting or checking sorted order would add work, so sortedness remains an explicit precondition.

Proposed takeaway: A count query can use boundary positions without enumerating all matching events. Two logarithmic searches still take logarithmic time.

Suggested follow-up: How would the cost change if each query received an unsorted log, or if I needed to return the matching events themselves?
