1. **Statement:** Measuring the elapsed time of one program on one computer gives a machine-independent measure of its efficiency.

   **Answer:** False. Hardware, interpreter, background work, and the input affect elapsed time. Counting basic operations as a function of input size helps compare growth without relying on one timing measurement.

2. **Statement:** For a search that stops at its first match, two inputs of the same length can require different numbers of comparisons.

   **Answer:** True. A match at the beginning takes one comparison; a missing value can require a full scan. The lecture's `search` returns early, whereas `linear_search` continues scanning even after finding a match.

3. **Statement:** An operation count of `3*n*n + 20*n + 7` has quadratic growth for large `n` under a unit-cost model.

   **Answer:** True. The quadratic term determines the growth rate. Lower-order terms and fixed coefficients affect concrete counts but do not change the quadratic classification.

4. **Statement:** Scanning an `n`-element list twice in sequence necessarily gives quadratic running time.

   **Answer:** False. Two complete scans do about `2*n` iterations, which is linear. Nested scans that each restart over the whole input have different costs.

5. **Statement:** Every pair of nested loops must take quadratic time in the input length.

   **Answer:** False. Count how often the body runs, rather than just counting loop levels. If an inner loop advances one shared index that never moves backward, its total iterations across all outer iterations can be bounded by `n`.

### 6. One-Minute Reflection

What idea from the OCW lecture did you transfer to this new problem? I used an operation-count argument. The shared index only advances and reaches the input length after exactly `n` increments.

Why my solution works: At the start of each outer iteration, all positions before the index have been grouped correctly. The inner loop consumes exactly the next consecutive run, stopping at a different label or the end. Appending its label and length extends the correct prefix. The index advances for every nonempty run, so the algorithm terminates. Empty input produces an empty result.

Time complexity: For `n` events and `r` runs, the index increments `n` times and the outer loop appends `r` tuples. With bounded label length, total time is O(n), including all run-boundary checks. Output space is O(r), at most O(n), and auxiliary space excluding the output is O(1). If label length is allowed to grow to `L`, string comparisons require a worst-case O(nL) bound. Functional tests establish the listed behaviors; the iteration argument establishes the complexity bound.

One thing I understand better now: Separate full scans add their costs, while repeated complete inner scans can multiply them. I need to inspect the actual index movement.
