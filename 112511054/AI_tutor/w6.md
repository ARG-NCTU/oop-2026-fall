### 題目與解答

#### 第 1 題：發布／訂閱

**題目：** 在 MOOS 架構中，一個應用程式一定要直接呼叫另一個應用程式的 C++ 成員函式，才能傳送導航資訊。

**答案：錯。**

MOOS 應用程式通常透過 MOOSDB 發布與訂閱具名變數，各程序可以獨立運行，不需要知道接收者的物件位址。這降低程序間直接依賴，但仍需要約定消息名稱、資料格式與意義。發布／訂閱並不代表可以完全不管通訊介面。

#### 第 2 題：目標速度與實際速度

**題目：** 巡航行為收到有效的速度更新後，目標速度可以改變；實際船速仍可能因加速或轉彎而暫時不同。

**答案：對。**

`WPT_UPDATE=speed=4.0` 更新行為的目標速度，不是直接把載具實際速度瞬間改成 4.0。控制器及模擬器會影響實際運動。既有測試也分別記錄更新消息與 `DESIRED_SPEED` 的出現時間，不能把消息、目標值與實際值混為一談。

#### 第 3 題：航點與航跡

**題目：** 只要把四個航點設成正方形，實際船隻航跡就一定具有四個精確的直角。

**答案：錯。**

航點定義的是導航目標，實際航跡還受到船隻轉向能力、控制參數、速度，以及 capture／slip radius 等因素影響。轉彎通常需要時間和半徑，因此航跡可能在角落變圓或偏離理想線段。

#### 第 4 題：行為更新通道

**題目：** `waypt_survey` 與 `waypt_return` 都使用 BHV_Waypoint，因此發送 WPT_UPDATE 就一定會同時修改兩者的速度。

**答案：錯。**

行為類型相同不代表更新通道相同。本次設定中，巡航使用 `updates = WPT_UPDATE`，返航使用 `updates = RETURN_UPDATE`。WPT_UPDATE 更新巡航配置；返航仍依自己的通道和原有 2.0 m/s 設定運作。需讀取具體配置，不能只根據類別名稱判斷。

#### 第 5 題：轉向控制

**題目：** 把航向 PID 的比例增益調得越大，船隻就一定轉得越快、越穩定，而且不會產生超越或震盪。

**答案：錯。**

增加比例增益通常會加強對航向誤差的修正，但過大可能造成超越與震盪。控制器產生舵角，模擬器再依其模型更新航向，兩者作用不同。應在相同條件下一次改一個參數，觀察實際航跡，不應把更大的參數直接視為更好的控制。

### ② My Misconception

- Before（常見誤解）：以為發送速度命令就會立即得到相同實際速度；以為正方形航點等於完美正方形航跡；以為同類型行為會自動共享所有更新。
- Now（觀念整理）：消息、行為目標與實際載具狀態分屬不同層次。發布／訂閱以具名通道交換資料，行為是否被更新取決於配置；運動結果還受到控制器與載具模型影響。

### ③ Challenge the AI

- Question examined：第 3 題，正方形航點是否一定產生精確直角航跡。
- Why：Oversimplified。
- Brief explanation：題目忽略了運動模型、有限轉向能力和航點捕獲條件。在理想的瞬間轉向模型中可以得到直角，但不能將這種假設直接套用到本週模擬船隻。

## Part B: LeetCode-style Lecture Code Transfer

### 1. Today’s Challenge

- Core concept from today’s lecture：透過消息更新封裝的任務狀態，使用基底回呼介面，再根據啟動條件產生決策結果。
- Coding challenge title：無人載具任務消息狀態機。
- 轉移來源：alpha.bhv 的 DEPLOY／RETURN 條件、巡航與返航速度的不同配置，以及 CMOOSApp 的 OnNewMail／Iterate 回呼模式。
- 題目定位：這是可獨立評測的 C++ 消息處理題，不連接 MOOSDB，也不模擬船舶運動、PID 或 IvP 效用函數。其轉移規則以下列規格為準。

#### Problem statement

依順序處理一艘載具的消息。任務有未出發、巡航、返航、完成四個階段；另有手動暫停旗標。初始未出發、手動旗標為 1、巡航目標速度為 3。返航速度固定為 2。

| 消息 | 更新規則 |
| --- | --- |
| `DEPLOY` | 開始新的巡航，清除返航、完成及手動旗標；保留最近設定的巡航速度。 |
| `RETURN` | 任務仍在執行時改為返航；未出發或已完成時忽略。手動暫停中也可記錄返航要求。 |
| `SPEED v` | 更新巡航目標速度；即使未出發或在返航中也保存，但不改變返航速度。 |
| `MANUAL b` | 設定手動旗標。手動期間任務階段保留，但輸出 PARK 0。 |
| `REACHED` | 任務執行且非手動時，巡航變返航、返航變完成；其他情況忽略。 |

全部消息處理完後，輸出模式及目標速度。未出發輸出 `PARK 0`；已完成輸出 `DONE 0`；執行中但手動暫停輸出 `PARK 0`；返航輸出 `RETURN 2`；巡航輸出 `SURVEY v`。完成與未出發的判定優先於手動旗標。

必須建立抽象回呼介面 `MessageApp`，提供 `OnNewMail` 與 `Iterate`，由子類別封裝並更新任務狀態。主程式透過基底參考呼叫回呼。

#### Input/output specification and constraints

- 第一行為消息數 n，接下來 n 行各為一個消息。
- 輸出一行模式與整數目標速度。
- `0 <= n <= 100000`；`0 <= v <= 4`；b 為 0 或 1；消息格式保證正確。

範例 1：

```text
輸入
3
DEPLOY
SPEED 4
REACHED
輸出
RETURN 2
```

巡航完成後進入返航，使用返航自己的速度。

範例 2：

```text
輸入
4
DEPLOY
MANUAL 1
REACHED
MANUAL 0
輸出
SURVEY 3
```

手動期間 REACHED 被忽略，恢復後仍是巡航。

範例 3：

```text
輸入
3
DEPLOY
REACHED
REACHED
輸出
DONE 0
```

#### Why the solution works and complexity

初始狀態符合題目。每個回呼按該消息的條件修改指定成員，其他成員保留，因此處理每個消息後都保持正確任務階段。輸出先處理未部署／完成，再處理手動、返航與巡航，符合規定優先順序。n 個消息的時間為 `O(n)`，只保存固定數量的狀態，額外空間為 `O(1)`。
