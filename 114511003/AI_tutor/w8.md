#### Question 1

Statement: When binary search looks for a value in a sorted list of `n` elements, it needs to inspect at most about `log₂ n` elements because each comparison eliminates about half of the remaining candidates.

#### Question 2

Statement: If a list is already sorted, linear search has `O(log n)` worst-case time because it can stop as soon as it sees a value greater than the target.

Answer: False.

Reason: If the target is greater than the largest element, linear search checks the whole list. Its worst-case time is `O(n)`.

#### Question 3

Statement: In merge sort, splitting the list in half at each step is enough by itself to make the whole algorithm `O(log n)`.

Answer: False. I initially knew the total was `O(n log n)` but could not explain why. After a follow-up question, I counted the work across a merge level.

Reason: For eight elements, the merge levels process `4 × 2`, `2 × 4`, and `1 × 8` elements. Each level handles all eight elements. Generally, each of about `log₂ n` levels takes `O(n)` work, giving `O(n log n)` total time.

#### Question 4

Statement: If bubble sort completes a full pass without swapping any elements, the list is sorted, so the algorithm can stop.

My first answer was False because I was thinking about an implementation that might run only once or lack a stopping check. After discussing what a full pass proves, I revised my answer to True.

Reason: A full pass compares every adjacent pair. If no pair needs a swap, all adjacent pairs are in order, so the entire list is sorted. An implementation needs to check the `swapped` flag to stop at that point.

#### Question 5

Answer: False.

Reason: One linear search takes `O(n)` worst-case time. Sorting once with merge sort and then searching takes `O(n log n + log n)` time. Sorting becomes more useful when the same sorted list supports many searches.

### 1. Today's challenge

Core concept from today's OCW lecture: Binary search narrows the candidate range in a sorted list by updating index boundaries.

AI-generated coding challenge title: Count Scores in a Range.

#### Problem statement

Given a sorted list of student scores and two integers `low` and `high`, return the number of scores satisfying `low <= score <= high`.

#### Input and output

- Input: A sorted list of integers `scores` and two integers `low` and `high`.
- Output: An integer count.

#### Constraints

- The list may be empty and may contain duplicate scores.
- `low <= high`.
- Aim for `O(log n)` search time, where `n` is the number of scores.

#### Examples

```text
scores = [40, 60, 60, 75, 90], low = 60, high = 75 -> 3
scores = [10, 20, 30], low = 21, high = 29 -> 0
scores = [], low = 0, high = 100 -> 0
```

### 3. AI Tutor help

I asked the AI Tutor for help, including a complete example solution.

The most useful idea was to find the first score `>= low` and the first score `> high`, then subtract their indices. I learned that `high` does not need to appear in the list. The index of the first value beyond `high` still marks the end of the range.

### 4. My revision

Yes, the approach changed. The AI-assisted version updates `left` and `right` indices instead of creating a new list slice at each step. It performs two boundary searches and subtracts their results. I have not rewritten the final program independently.

The AI-assisted program used for verification is:

```python
def search(L, low, high):
    def first_at_least(target):
        left, right = 0, len(L)
        while left < right:
            mid = (left + right) // 2
            if L[mid] < target:
                left = mid + 1
            else:
                right = mid
        return left

    def first_greater(target):
        left, right = 0, len(L)
        while left < right:
            mid = (left + right) // 2
            if L[mid] <= target:
                left = mid + 1
            else:
                right = mid
        return left

    return first_greater(high) - first_at_least(low)
```

Why the program works: The first boundary is the index of the first value inside or above the range. The second is the index immediately after the last value inside the range. All matching scores occupy the positions between them, so the count is their index difference.

Time complexity: `O(log n)` for each boundary search, hence `O(log n)` overall.  
Space complexity: `O(1)` extra space, because the searches update indices without slicing or recursion.
