#### Initial answers and reasoning — supplied by the user

**1. 程式間通訊：對**
同一個 community 是星狀結構：每個應用程式只連到 MOOSDB，用 `Register` 訂閱變數，用 `Notify` 發布，由 MOOSDB 轉送。應用程式之間不必兩兩建立連線。
但「不必直接連線」不等於「完全不用連線」，每個程式仍然要連到 MOOSDB。跨 community 則要靠 pShare 這類橋接程式。

**2. Backseat Driver 架構：錯**
這個架構的重點正是把兩者分開。
- **後座：**MOOS-IvP（例如 pHelmIvP）只負責高階決策，輸出期望的航向、速度、深度（`DESIRED_HEADING` 等）。
- **前座：**載具廠商原本的控制系統，負責低階致動器控制，並把導航資料回傳給後座。

分開的好處是自主軟體可以換到不同平台，前座也能保留自己的安全機制。

**3. 更新時間：錯**
NAV_X 和 NAV_Y 是兩則獨立的訊息，各自有時間戳。可能出現以下情況：
- 兩者在不同輪 iteration 才收到；
- NAV_Y 一直沒更新，保存的是舊值；
- NAV_Y 從來沒收到。

要確認兩者是否屬於同一時間點，必須比對各自的時間戳（`msg.GetTime()`）。光是收到 NAV_X 不能保證任何事。

**4. 設定檔更新：錯**
大多數 MOOS 程式只在啟動時（`OnStartUp`）讀一次 `.moos`，pHelmIvP 也只在啟動時讀 `.bhv`。程式啟動後才改磁碟上的檔案，通常要重新啟動程式才會生效，除非該程式自己寫了重新讀取的機制。
執行中要調整參數，一般是發布 MOOS 變數，例如行為的 `updates=` 變數，而不是改檔案。所以一定要先確認程式「如何、何時」讀設定。

**5. 設定與實際執行：錯**
設定檔只代表「預期」，實際行為還取決於很多因素：
- 模式條件有沒有成立（例如 `DEPLOY=true`、`RETURN=false`）；
- 行為之間的優先權和衝突；
- capture radius 的設定；
- 洋流、障礙物、致動器失效等環境與硬體狀況。

要證明載具真的依序到達航點，必須觀察執行狀態與軌跡，例如用 alog 記錄看 NAV_X/NAV_Y、`WPT_INDEX`、`WPT_STAT`，或在 pMarineViewer 上看實際路徑。

## Part B: Lecture Concept Transfer

### 1. Today's Challenge

**Title: Navigation Snapshot Monitor**

以 Python 設計 `NavigationMonitor`，練習將獨立到達的變數更新累積為物件狀態。這是概念練習，不連接真正的 MOOSDB，不視為完成 MOOS-IvP 部署或實際任務驗證。

介面與規格：

- `NavigationMonitor()`：建立空狀態；每個物件的資料互相獨立。
- `update(name, value)`：只接受名稱 NAV_X、NAV_Y。對接受的名稱保存最新值並回傳 True；其他名稱回傳 False，狀態不變。
- `ready()`：只有 NAV_X 與 NAV_Y 都曾收到，才回傳 True。值為 0 仍算已收到。
- `snapshot()`：回傳目前收到的變數與值所組成的新 dictionary；外部修改它不影響物件內部資料。
- `reset()`：清空狀態，之後 ready() 為 False；不得改變先前已取得的 snapshot。

Constraints:

- name 為字串；value 保證為有限的 int 或 float（不含 bool）；本題不需要另做數值型別驗證。
- 最多 1000 次更新，保留每個被接受名稱最後一次傳入的值。
- 只用已學過的類別、dictionary、條件判斷等；不使用外部套件。
- ready() 只表示兩個欄位都有值，不表示它們具有相同時間戳或足夠新鮮。

Examples:

1. 新建物件 ready() 為 False、snapshot() 為 {}；update('NAV_X', 0) 為 True，ready() 仍為 False；再 update('NAV_Y', 3)，ready() 為 True、snapshot() 為 {'NAV_X': 0, 'NAV_Y': 3}。
2. 依序 update('NAV_X', 1)、update('NAV_X', 5)，snapshot() 為 {'NAV_X': 5}，ready() 為 False。
3. update('OTHER', 9) 為 False，狀態不變；reset() 後 snapshot() 為 {}、ready() 為 False。

Additional verification: 兩個物件相互獨立；修改回傳 snapshot 不影響原物件；reset 不改變舊 snapshot；任一更新順序都能正確判斷 ready。

### 2. My Initial Approach — Before AI Help

使用者提供的解題思路：

- **保存狀態：**每個物件在 `__init__` 中建立自己的 dict `_state`，key 是變數名稱，value 是最新值。重複更新時直接覆蓋，自然就是保留最後一次的值。
- **判斷是否齊全：**檢查兩個 key 是否都在 dict 中（`in`），**而不是檢查值的真假**。如果寫成 `if self._state.get("NAV_X")`，值為 0 時會被誤判成「沒收到」。
- **確保獨立：**
  - **物件之間：**dict 在 `__init__` 中建立，屬於實例。不能寫成類別屬性 `_state = {}`，否則所有物件會共用同一個 dict。
  - **snapshot：**回傳 `dict(self._state)`，也就是一個新的 dict。因為值都是數字（不可變），淺拷貝就夠了。
  - **reset：**`clear()` 只清空物件內部的 dict，先前回傳的 snapshot 是另一個 dict，不受影響。

### 4. My Revision

- Approach / code changes: 解法及測試邏輯未改，原始檔以 UTF-8 LF 保存。
- Program and original verification script: [nav_monitor.py](nav_monitor.py)

```python

class NavigationMonitor:
    _FIELDS = ("NAV_X", "NAV_Y")

    def __init__(self):
        self._state = {}          # 每個物件各自建立自己的 dict

    def update(self, name, value):
        if name not in self._FIELDS:
            return False          # 未知名稱：狀態不變
        self._state[name] = value # 重複更新 → 覆蓋為最新值
        return True

    def ready(self):
        # 以「key 是否存在」判斷，而非值的真假，所以 0 也算收到
        return all(f in self._state for f in self._FIELDS)

    def snapshot(self):
        return dict(self._state)  # 回傳新 dict（值皆為不可變數字，淺拷貝即可）

    def reset(self):
        self._state.clear()

```

### 7. Correctness, Complexity and Concept Transfer

以下為使用者提供的完整說明：

**為什麼符合規格：**

| 規格 | 做法 |
|---|---|
| 只接受兩種名稱 | `_FIELDS` 白名單，其他名稱在修改狀態前就回傳 `False` |
| 保存最新值 | dict 覆蓋 |
| 0 也算收到 | `ready()` 用 `in` 判斷 key 是否存在 |
| snapshot 與 reset 互不影響 | snapshot 每次建立新 dict；reset 只清內部 dict |
| 物件獨立 | `_state` 是實例屬性，不是類別屬性 |

**各方法的複雜度**（欄位數 k ≤ 2，視為常數）：

| 方法 | 時間 | 額外空間 |
|---|---|---|
| `__init__` | O(1) | O(1) |
| `update` | O(1)（dict 平均） | O(1) |
| `ready` | O(1) | O(1) |
| `snapshot` | O(k) = O(1) | O(k) = O(1)（新 dict） |
| `reset` | O(k) = O(1) | O(1) |

**n 次更新：**總時間 **O(n)**。由於只保留最新值，不論 n 多大，物件本身的空間都是 **O(1)**。

**與 MOOS 概念的對應：**
- **獨立到達的訊息：**每次 `update(name, value)` 對應 `OnNewMail()` 收到的一則訊息。NAV_X 和 NAV_Y 各自發布、各自到達，順序和頻率都不保證。所以要測「先 Y 後 X」和「只收到一種」。
- **應用程式保存的狀態：**`_state` 相當於 MOOS 應用程式的成員變數（例如 `m_nav_x`、`m_nav_y`、`m_got_x`）。程式在 `OnNewMail()` 中更新狀態，再由 `Iterate()` 根據累積的狀態做計算。
- **`ready()`：**相當於 `Iterate()` 開頭的「兩個值都收過了嗎？」檢查。但它和第 3 題一樣，**不代表時間同步或資料新鮮**。實務上若要判斷，需要額外保存每個變數的時間戳並比對時間差。
- **`snapshot()`：**相當於在某一輪計算開始時把狀態複製一份。之後再進來的訊息不會改到正在使用的資料。

AI clarification: 固定兩個欄位且採字典操作平均常數時間模型，各方法可視為 O(1)，n 次更新為 O(n)，狀態空間 O(1)。snapshot 與後續狀態修改分離；此單執行緒練習沒有額外提供多執行緒原子性保證。
